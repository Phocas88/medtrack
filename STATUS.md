# Invexiqs implementation status

> This is the baseline audit of commit `14a352c`. Implementation has since started on `codex/stokora-commercial-hardening-20261115`; see [COMMERCIAL_READINESS.md](COMMERCIAL_READINESS.md) for changes, remaining gaps and rollout gates. The baseline ratings below are historical, not the current branch status.

Audited 2026-11-15. Repository: `Phocas88/medtrack`, branch `master`, commit `14a352c32fa4c8e03f5948e5b6146f7e8e9fa3c6`. The repository has not been renamed; its package is `stokora-wms`.

**Assessment: a substantial warehouse application prototype with real Supabase CRUD and some real external API calls, but not yet a reliable self-service paid SaaS or a Shopify App Store-ready app.** Core catalog and inventory screens are implemented. Payment conversion, tenant permissions, Shopify onboarding/synchronization, and database reproducibility have material gaps. Some convincing integration and operational screens simulate success.

## Audit scope and meaning of ratings

This report follows source handlers, database queries, mutations, and SQL migrations rather than documentation or feature names. **Working** means an implemented code path consistent with the checked-in schema for the stated scope; it does not mean production execution was proven. **Partial** means real functionality exists but an important part is broken, missing, unsafe, or dependent on untracked schema. **Placeholder** means the advertised capability is simulated or only browser-local rather than a shared service.

No application code was changed. Env files and credential files were not read, and secret values are omitted. Dependencies were installed for static checks. No production signup, payment, seed, email, or other state-changing API was exercised. Live inspection was limited to unauthenticated GETs of `/` and `/demo`. Production credentials, Supabase schema/policies, provider configuration, and Vercel deployment settings were not inspected; they may differ from this commit.

## 4. New visitor → paid subscription

1. **Arrival is broken for acquisition.** Live `/` redirects to `/auth/login`, matching middleware. Marketing pricing is unreachable to signed-out visitors. `/demo` renders publicly, but claims broader functionality than code supports.
2. **Signup form exists.** Login links to `/auth/signup`; it validates input client-side and calls Supabase Auth. Email confirmation and redirects depend on external Supabase configuration; signup supplies no explicit confirmation callback URL.
3. **Tenant bootstrap is implemented but unsafe/non-atomic.** Browser sends user ID/email/company to a public service-role endpoint. It creates the tenant and admin row without verifying the caller's identity. Profile failure deletes the tenant, but leaves Auth identity behind; no resume/reconciliation path is supplied.
4. **Confirmation/login requires external setup.** If confirmation is enabled, the UI asks the user to check email. No delivery was verified. `/auth/callback` exchanges a code. Already authenticated `/auth/*` requests are redirected before their pages/handlers, which also interferes with recovery.
5. **Onboarding runs before app/billing.** Signup navigates to dashboard; `OnboardingGate` redirects an unconfigured tenant to onboarding. Wizard creates real entities and sets completion, but its first save discards existing settings. No tenant/profile causes a blank gate instead of recovery.
6. **No actual free-trial lifecycle.** No trial end date, Checkout trial period, expiration enforcement or conversion automation was found. “Free trial” is marketing copy.
7. **Subscription purchase is broken from the UI.** `/billing` shows $49/$99/$199 plans, but sends hard-coded placeholder price IDs. Creating real Stripe prices/environment mappings alone does not change those UI constants. Provider key, real prices, webhook URL/secret and portal settings require manual external setup.
8. **Checkout server call is real but unauthorized.** It accepts arbitrary client tenant/price IDs, trusts the request origin for return URLs, does not reuse an existing customer, and does not prevent duplicate subscriptions. Returns to settings rather than a verified billing-completion screen.
9. **First payment can update JSON, but later events are disconnected.** Signed checkout completion retrieves the subscription and writes `settings.billing`. Checkout never sets `subscription_data.metadata.tenantId`; subscription update/deletion/failure handlers expect it. Failures are swallowed with 200, losing retry recovery.
10. **Payment does not govern service access.** No server-side enforcement of plan, trial, user/location/product/order limits or cancelled/past-due status was found. Tenant users can directly update the same settings containing billing status. General settings save can erase that status and integration configuration.

**Result:** there is no complete, trustworthy signup-to-paid path in this commit. A developer could manually configure prices and collect a subscription through the API, but reliable lifecycle accounting and entitlement enforcement are still missing.

## 7. Quality, bugs and security

### Checks performed

- Dependency installation completed with lifecycle scripts disabled and a temporary writable npm cache.
- TypeScript: `tsc --noEmit --incremental false` reported **zero errors**.
- ESLint: **zero errors, 29 warnings**, primarily hook dependencies and image optimization.
- Playwright discovery: **102 tests in 18 files**. They mostly check public rendering, redirects, endpoint presence, headers and invalid credentials. Some accept HTTP 500 as an acceptable security result. No successful paid lifecycle, warehouse posting/concurrency, tenant-role isolation, cost protection or Shopify sync tests were found.
- Vitest discovery fails because it collects Playwright files using an incompatible test API. `npm test` selects Vitest; there are no separate unit test files/configuration establishing useful unit coverage.
- Browser E2E tests and production build were **not run**; credentials/configuration were not supplied or inspected. No coverage percentage is available, and no CI workflow was found. Passing static checks does not validate SQL payloads because queries are not tied to generated schema types.

### Highest-severity source findings

1. **Unauthenticated recovery-link disclosure:** `api/portal/invite/route.ts` uses service role without authenticating a caller and returns an actionable account recovery link, including for an existing Auth user. Knowing a matching customer/tenant ID can permit account takeover. Rate limiting does not authorize the operation.
2. **Public billing/payment and pickup operations:** Stripe checkout/portal, POS charge and EasyPost pickup lack user/tenant authorization. Billing portal can expose management of another tenant's Stripe customer when its tenant ID is supplied. Shipping buy has an ID-only service-role order update. See their API routes.
3. **Forged/misrouted Shopify webhooks:** main order handler trusts headers/body with no HMAC. Domain helpers compare substrings, including empty stored strings, so an unconnected tenant can match. GDPR/uninstall checks fail open when the secret is absent. `src/app/api/shopify/webhook/route.ts`, `src/lib/shopify-webhooks.ts`.
4. **Roles, secrets and billing share client-writable settings:** tenant RLS permits all roles to read/write tenant JSON; QuickBooks secret and Zapier key are stored there, Shopify token may be plaintext without encryption configuration. Managers can promote themselves; inactive users remain authorized. `supabase/migrations/00001_initial_schema.sql`, auth helpers, integration pages.
5. **Inventory has multiple unsynchronized sources of truth:** dashboard stock sums lots, while Shopify/POS/other flows often write movements only. No SQL movement-to-stock trigger reconciles them. Shipment decrements do not reconcile bin inventory. Browser read/modify/write has no locking or atomic rollback. `A/ship/page.tsx`, POS page, Shopify webhook, migrations.
6. **Silent success after SQL/provider failure:** Supabase often returns `{ error }` rather than throwing, but many flows ignore it. Specific failures include Shopify orders without required customer, null-product administrative movements, generated cycle-count variance writes, and portal's `pending` status/incorrect order-line fields. Stripe/GDPR handlers can acknowledge failed processing with 200.
7. **Destructive settings writes:** onboarding and general settings replace the whole JSON object, erasing Shopify, billing and completion/module state. `A/onboarding/page.tsx`, `A/settings/page.tsx`.
8. **Public demo can reach real external services:** demo launches shared real Auth accounts; billable/email routes do not isolate a demo tenant or use a server-enforced simulation boundary. Production seed guard is useful but does not protect those APIs. Provider configuration was not inspected, so actual exposure is unknown.

Additional concerns: arbitrary Shopify shop/store URLs are used in server fetches without enforcing a valid Shopify hostname; retry/event processing lacks durable queues; browser-local wave/dock/cross-dock state uses global keys across tenant switches; HTML email/print templates interpolate stored input without systematic escaping; CSV export does not enable formula escaping. Default Postgres views are not declared `security_invoker`; verify actual grants and view ownership before exposing them. Sentry config files and a dependency exist, but `next.config.mjs` has no `withSentryConfig` and no instrumentation file was found, so complete monitoring is unverified.

The most useful unfinished-work markers are executable behavior rather than TODO counts: mock recall scans, unconditional QuickBooks success, local/mock Zapier logs, “Import coming soon,” discarded recovery links, and inventory webhooks that only log. A public demo claim of “100% WMS compliant” is unsupported by these implementations.
